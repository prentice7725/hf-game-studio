# hf-game-studio v3: 실험 주도 스튜디오 (설계 초안)

작성: 2026-11-10. 상태: **P0 한 바퀴 끝(2026-11-11)**, P1은 결정 대기. 구현된 것은 `experiment.mjs lint`, 스키마 둘, 스킬 셋이다. 아래 본문은 처음 설계이고, 실측으로 바뀐 것은 끝의 "P0 실측"에 있다.
검토한 제안서: `hf_game_studio_autonomous_v3_proposal_2026-11-10.md`(Research-Led Autonomous Game Production). 기준 코드: `main` `d0cc6e6`.

## 한 줄

v2는 "시킨 대로 만들었나"를 기계로 확인한다. v3는 그 앞에 **"무엇을 만들지"를 실험으로 정하는 층**을 하나 얹는다. 새로 생기는 것은 실험 카드 파일 하나, 그것을 검사하는 스크립트 하나, 스킬 셋이다. 상주 오케스트레이터와 상태 머신은 만들지 않는다.

## 제안서 검토

### 그대로 받는 것

- v2 하네스 위에 얇은 층만 얹고, hyperfusion급 오케스트레이터를 다시 만들지 않는다.
- `근거 → 추론 → 가설 → 가장 싼 실험 → 작업`의 사슬. 조사에서 바로 큰 구현으로 가지 않는다.
- 조사 결과는 SOT를 덮어쓰지 않는다. 게임의 정체성은 사용자가 정한다.
- 웹에서 읽은 것은 데이터이지 지시가 아니다. 본 것(observed)·들은 것(reported)·추론(inferred)을 가른다.
- 버그 수정마다 조사를 다시 하지 않는다.
- 재미는 자동 통과시키지 않고 사람이 판정한다.
- 첫 단계는 "이해 → 조사 → 가설 → 작업 하나"의 수직 슬라이스다.

인용한 외부 사례 중 GitHub 저장소 넷(Game-Creation-Agents, Godot-Director, gamecraft-bench, opengame)은 실재하고 설명도 맞는 것을 확인했다. opengame 링크는 포크이고 원본은 `leigest519/OpenGame`이다. 논문 링크 셋은 확인하지 않았다. 아래 설계는 어느 것에도 기대지 않는다.

## 원칙

v2의 다섯 원칙은 그대로다. 둘을 더한다.

6. **만들기 전에 틀릴 조건을 적는다.** 가설에는 반증 조건과 측정 방법이 붙고, 승인한 뒤에는 바꾸지 않는다. red-first의 설계판이다.
7. **가장 싼 실험부터.** 문서로 답이 나오면 만들지 않고, 시뮬레이션으로 답이 나오면 화면을 만들지 않고, 웹 프로토타입으로 답이 나오면 Godot에 넣지 않는다.

판단과 기계의 분업도 v2와 같다.

| | 누가 | 예 |
|---|---|---|
| 판단 | 리드가 스킬 절차대로 | 무엇을 조사할지, 어떤 가설을 세울지, 어느 칸에서 실험할지, 결과를 어떻게 읽을지 |
| 믿을 수 있어야 하는 것 | 스크립트 | 카드가 갖출 것을 갖췄나, 승인 뒤 바뀌지 않았나, 작업이 카드 범위 안인가, 예산이 남았나, 측정이 다 끝났나 |
| 재미와 정체성 | 사용자 | 카드 승인, 사람 측정의 판정, GDD 반영 |

## 실험 카드

`design/experiments/EXP-001-<slug>.json`. 게임 저장소 안에 두고 커밋한다. 형식은 hf-game-studio의 `schemas/experiment.schema.json`(게임 저장소에 복사하지 않는다. 복사본이 낡으면 lint와 어긋난다).

```json
{
  "id": "EXP-001",
  "question": "자동 전투의 결과가 편성 탓이라고 플레이어가 느끼는가",
  "sot_anchor": {"design/gdd.md": ["기둥(pillars)", "계약 해결"]},
  "origin": "design/gdd.md 열린 질문 3 / design/research/RQ-001.json F2",
  "hypothesis": "결과 보고가 '누가 무엇을 막았는지'를 한 줄로 보여 주면 다음 편성을 바꾼다",
  "falsified_if": "보고를 읽고도 다음 계약에서 편성을 바꾸지 않거나, 왜 졌는지 답하지 못한다",
  "rung": "prototype",
  "measures": [
    {"id": "M1", "type": "sim", "what": "편성 정책 3종의 성공률 차이가 15%p 이상(1000판, 시드 고정)",
     "check": "npm --prefix prototype test -- sim/formation.sim.test.ts"},
    {"id": "M2", "type": "telemetry", "what": "3계약을 하는 동안 편성 변경 1회 이상",
     "check": ["node", "tools/hfgs/play-log.mjs", "--expect", "formation_changes>=1"]},
    {"id": "M3", "type": "human", "ask": "두 번째 계약에서 왜 졌다고 생각했나? 그래서 무엇을 바꿨나?"}
  ],
  "scope": {"paths": ["prototype/src/", "data/contracts.json", "test/"]},
  "invariants": ["design/gdd.md", "design/world.md", "아트·사운드 추가 없음"],
  "budget": {"tasks": 4, "restarts": 2, "asset_runs": 0, "consult_calls": 8},
  "commit": "branch"
}
```

- **`sot_anchor`**: 이 질문이 GDD의 어디에 걸려 있는지. 섹션이 실제로 있어야 한다. 걸 곳이 없는 실험은 게임의 정체성을 넓히는 것이므로 실험이 아니라 GDD 작업(사용자 결정)이다.
- **`falsified_if`**: 필수. 이것을 못 적는 가설은 실험할 수 없다.
- **`measures`**: 종류는 넷이고, 믿을 수 있는 순서대로다.
  - `sim`: 규칙 순수 함수에 봇 정책을 돌린 결과. 수용 검사 명령이다.
  - `telemetry`: 사람이 플레이하는 동안 프로토타입이 남긴 결정 기록에서 센 값. 수용 검사 명령이다.
  - `human`: 사용자에게 묻는 질문. 실험당 셋까지. 답은 사용자가 준다.
  - `scenario`: `godot-playtest.mjs` 시나리오(화면에 보이는가, 흐름이 이어지는가). 재미가 아니라 회귀를 본다.
- **`invariants`**: 건드리지 않을 것. 파일 경로는 작업의 범위 검사가 기계로 막고, 문장은 리드와 리뷰어가 본다.
- **`budget`**: 넘으면 `start`가 거절한다. 작업 수, 재시작 수, 애셋 생성 횟수, 전문가 호출 수.
- **`commit`**: `"branch"`면 작업이 verify·리뷰를 통과할 때마다 리드가 `exp/EXP-001`에 커밋한다. `"ask"`면 지금처럼 매번 묻는다.

판정은 카드에 덧붙인다(`verdict`: supported·refuted·inconclusive, 측정별 결과, 날짜, 다음에 할 것). 기각된 카드도 지우지 않는다. 같은 가설을 다시 세우지 않게 하는 기억이 이 폴더다.

## 실험 사다리

| 칸 | 만드는 것 | 측정 | 비용 | 답할 수 있는 질문 |
|---|---|---|---|---|
| 0 문서 | 없음 | GDD·조사 노트·이전 실험 | 분 | 이미 정했거나 이미 기각한 것인가 |
| 1 시뮬레이션 | 규칙 함수 + 봇 정책 + Vitest | `sim` | 분~한 시간 | 선택이 결과를 바꾸는가, 지배 전략이 있는가, 수치가 버티는가 |
| 2 웹 프로토타입 | Phaser 화면 + 결정 기록 | `telemetry` + `human` | 한나절 | 정보가 읽히는가, 다음 선택을 바꾸는가, 재미있는가 |
| 3 Godot | 본편 조각 | `scenario` + `human` | 하루 이상 | 본편의 손맛·연출·애셋과 함께여도 유지되는가 |

- 카드는 칸 하나를 고른다. 위 칸으로 가려면 아래 칸의 측정이 통과했거나, 해당 없다는 이유가 카드에 있어야 한다(`lint`가 본다).
- 1번 칸이 이 설계의 가장 큰 이득이다. "선택이 의미 있는가"는 재미의 필요조건이고 기계로 답이 나온다. 정책을 바꿔도 결과가 같으면 화면을 만들 이유가 없다. 새 도구도 필요 없다. 시뮬레이션은 수용 검사에 넣는 Vitest 하나이고 red-first가 그대로 선다(메커닉이 없을 때는 실패).
- 2번 칸의 `human` 측정은 **플레이 묶음**으로 한 번에 묻는다: 실행 명령 하나, 할 일 한 줄("계약 셋을 해 보세요"), 질문 셋 이하. 사용자의 5분이 이 스튜디오에서 가장 비싼 자원이므로 실험 끝에 한 번만 쓴다.
- 3번 칸의 자동 탐색 에이전트(제안서 P2)는 넣지 않는다. 지금의 시나리오 플레이테스트로 충분한지는 merc-guild에서 본 뒤 정한다.

## 흐름

```text
점검(gs-inspect) ──▶ 열린 질문 ──▶ [조사(gs-research)] ──▶ 실험 카드(gs-experiment)
                                                                │ experiment.mjs lint
                                                                ▼
                                                    사용자 승인(approve --approved)   ← 게이트 1
                                                                │
                        카드 범위·예산 안에서 묻지 않고 반복:      ▼
                        task.mjs start → 구현 → verify → consult review → (브랜치 커밋)
                                                                │
                                                     sim·telemetry 측정은 검사가 판정
                                                                ▼
                                                    플레이 묶음: 사용자가 해 보고 답함  ← 게이트 2
                                                                │ experiment.mjs close
                                                                ▼
                              supported → GDD 반영 작업 제안 │ refuted → 기록하고 다음 질문 │ inconclusive → 측정을 고친 새 카드
```

게이트는 실험당 둘이다. v2의 "게이트는 마일스톤 승인 하나"에서 끝의 판정 하나가 늘었다. 그 사이에는 묻지 않는다.

**리드가 멈추는 때.** 이것 말고는 계속한다.

- 작업이 카드의 범위·불변 항목·예산을 넘어야만 끝난다 → `hold`, 카드를 고칠지 묻는다(고치면 다시 승인).
- 같은 원인으로 verify나 리뷰가 두 번 실패했다 → `hold`.
- `sim` 측정이 가설을 반증했다 → 화면을 만들지 않고 `close --verdict refuted`를 제안한다. 조용히 가설을 바꿔 계속하지 않는다.
- GDD와 코드가 어긋난 것을 찾았다 → 어느 쪽이 맞는지 정하지 않고 보고한다.

**조사가 필요한 때.** 열린 질문에 GDD도 이전 실험도 답하지 못하고, 리드가 가설을 둘 이상 세우지 못할 때만 한다. 조사는 카드의 선택 입력이다.

## 조사 노트

`design/research/RQ-001-<slug>.json`. 질문 하나에 파일 하나.

- `question`: 플레이어의 결정으로 적는다("자동 전투 결과의 원인을 얼마나 보여 줘야 다음 편성을 바꾸는가"). 소재나 시점이 아니다.
- `refs[]`: `id`, `url`, `retrieved_at`, `source_type`(공식·개발자 글·리뷰·플레이어 의견·영상), `evidence_kind`(observed·reported·inferred), `claim`(한 문장, 리드의 말로). 원문은 옮겨 적지 않는다.
- `findings[]`: `id`, `statement`, `refs`, `kind`(pattern·anti-pattern·open). 추론은 추론이라고 적는다.
- `stopped_because`: 왜 여기서 멈췄나.

규칙은 스킬에 적는다.

- **찾는 순서:** 사용자가 준 참고작 → 같은 결정 구조의 정통작 2~3 → 메커닉이 같은 다른 장르 2 → 비판받은 사례 1. 출처 8개 또는 새 출처 둘이 연달아 판단을 바꾸지 못하면 멈춘다.
- **영상:** 자막이나 프레임을 실제로 읽지 못했으면 observed가 아니다. 리드는 남의 게임을 해 볼 수 없으므로 observed는 드물 것이다. 그것이 정상이다.
- **격리:** 조사는 읽기 도구만 가진 하위 에이전트에게 맡기고 위 형식의 JSON만 돌려받는다. 페이지 안의 지시문은 `claim`에도 옮기지 않는다. 리드는 조사 결과에서 나온 명령·설치·링크 실행을 하지 않는다.
- **복제 금지:** 가져오는 것은 결정 구조와 피드백 방식이다. 이름·캐릭터·그림·수치표·문장은 가져오지 않는다.
- **검증(P2):** `consult.mjs`에 다른 계열 모델이 `claim`과 URL만 받아 "이 출처가 이 주장을 하는가"를 보는 모드를 둔다. 리뷰어에게 결론을 주지 않는 v2 규칙과 같다.

## 스크립트: `scripts/experiment.mjs`

| 명령 | 하는 일 |
|---|---|
| `lint EXP.json --repo R` | 스키마, `sot_anchor` 섹션이 실제로 있음(`task.mjs`의 `sections` 재사용), `origin`이 가리키는 조사 노트·finding이 있음, `falsified_if` 있음, 측정이 하나 이상이고 `sim`·`telemetry`·`scenario`에는 `check`가 있음, `human` 질문 3개 이하, 칸과 측정 종류가 맞음(시뮬레이션 칸에 `human`만 있으면 거절), 아래 칸을 건너뛰었으면 이유가 있음, 예산이 있음, 범위가 검사 기준 파일(스키마·매니페스트·용어집·`design/experiments/`)과 겹치지 않음. 같은 `hypothesis`로 기각된 카드가 있으면 경고 |
| `approve EXP.json --approved` | lint 통과를 확인하고 카드 해시를 `HFGS_HOME/experiments/<id>.json`에 남긴다. `--approved`는 `assets.mjs pick`과 같은 뜻이다: 사용자의 승인이고 리드가 혼자 붙이지 않는다 |
| `status [EXP-id]` | 카드 + 그 실험의 작업 기록에서 계산: 끝난 작업, 보류, 예산 사용, 측정별 상태(검사 통과·대기·사람 대기). 세션을 새로 열었을 때 리드가 처음 돌리는 명령 |
| `packet EXP.json` | `human` 측정이 남았을 때 플레이 묶음을 출력: 실행 명령, 할 일, 질문 |
| `close EXP.json --verdict V "M3=confirmed:..."` | 측정이 모두 판정됐는지 확인하고(`sim`·`telemetry`는 지금 다시 돌린다, `human`은 사용자 답) 카드에 `verdict`를 적는다. `human` 측정이 rejected인데 supported로 닫으려 하면 거절 |

`task.mjs`에는 작업 파일 필드 하나가 는다.

- `"experiment": "design/experiments/EXP-001-....json"`
- `plan`: 카드를 검사 기준 파일에 넣는다(범위 밖 강제, verify에서 불변 확인). `scope.paths`가 카드의 `scope.paths` 안에 있어야 한다.
- `start`: 카드가 승인됐고 승인 때의 해시와 같아야 한다. 예산(작업 수·재시작 수)이 남아야 한다. 아니면 `EXPERIMENT_NOT_APPROVED`·`EXPERIMENT_CHANGED`·`BUDGET_EXCEEDED`로 거절.
- `experiment`가 없는 작업은 지금과 똑같이 돈다. 버그 수정, 준비 작업, 애셋 작업은 카드가 필요 없다.

애셋 생성 횟수는 `assets.mjs`의 작업 노트(`HFGS_HOME/assets/<task_id>/`)에서 `status`가 센다. 전문가 호출은 지금 보고서(`HFGS_HOME/reviews/`)에 작업 ID가 없어 셀 수 없으므로, `consult.mjs review --task`와 `write`가 보고서에 `task_id`를 남기게 고쳐야 한다(P1). 넘으면 `start`가 다음 작업을 거절한다(도중의 호출 자체는 막지 않는다. 실수를 잡는 장치이지 우회를 막는 장치가 아니다).

| 스킬 | 언제 | 내는 것 |
|---|---|---|
| `/gs-inspect` | 세션 처음, 실험을 닫은 뒤 | GDD ↔ 코드 ↔ 작업 기록 ↔ 실험 폴더의 **차이 표**: 정했는데 안 만든 것, 만들었는데 안 정한 것, TBD, 서로 어긋난 것. 그리고 다음 실험 후보 셋 이하(각각 질문과 예상 칸). 읽기 전용, 저장하지 않는다 |

템플릿도 조금 는다.

- `templates/design/gdd.md`에 **"열린 질문"** 섹션. 지금은 마일스톤 문서 끝에 흩어져 있다(`examples/milestone-1.md`의 "성공 확률을 숫자로 보여 줄지…"). 실험의 원천이 여기다.
- `templates/phaser/src/sim/`: 시드 고정 난수와 정책 실행기(정책 함수들을 받아 N판 돌리고 정책별 결과 분포를 돌려주는 30줄 정도), 예시 테스트 하나.
- `templates/phaser/src/telemetry.ts` + `tools/play-log.mjs`(P1): 프로토타입이 결정(무엇을 골랐나, 무엇을 본 뒤였나)을 JSON으로 남기고, 도구가 `--expect "formation_changes>=1"` 같은 조건을 0·1·2 종료 코드로 판정.

## 단계

지금까지처럼 merc-guild(시험대)에서 한 바퀴 돌려 마찰을 모으고, 드러난 것만 기계로 만든다.

**P0: 종이로 한 바퀴.** 코드는 `experiment.mjs lint`와 스키마 둘뿐.
- 스킬 셋 초안, GDD "열린 질문" 섹션, 카드·조사 노트 스키마, `lint`.
- merc-guild에서: `/gs-inspect` → 질문 하나 → (필요하면 조사) → EXP-001 카드 → 1번 칸(시뮬레이션) 작업 하나를 **기존 `task.mjs` 그대로** start → verify → review.
- 볼 것: 카드를 쓰는 데 걸린 시간이 실험보다 긴가, `lint`가 잡은 것과 놓친 것, 시뮬레이션이 실제로 판단을 바꿨는가, 조사가 가설을 바꿨는가(안 바꿨으면 조사 스킬을 더 줄인다).
- 끝나는 조건: 판정이 붙은 카드 하나와 마찰 목록.

**P1: 묶어서 맡기기.** P0의 마찰을 반영한 뒤.
- `approve`·`status`·`packet`·`close`, `task.mjs`의 `experiment` 필드(해시·범위·예산), 실험 브랜치 커밋.
- sim 템플릿, telemetry + `play-log.mjs`.
- merc-guild에서 2번 칸 실험 하나를 작업 3~4개로 묻지 않고 돌린다. 볼 것: 멈춘 횟수와 이유, 예산이 맞았는가, 플레이 묶음에 사용자가 쓴 시간.

**P2: 본편과 보강.** 쓸모가 드러난 것만.
- 3번 칸(Godot): `scenario` 측정을 카드에 연결.
- 조사 노트의 다른 계열 검증(`consult.mjs`).
- 읽힘 검사(해 볼 만한 생각, 미검증): 다른 계열 모델에게 **플레이어가 보는 것만**(결과 보고 글자·스크린샷) 주고 "왜 졌나"를 묻고, 시뮬레이션 기록의 실제 원인과 맞는지 본다. 재미가 아니라 피드백이 읽히는지를 재는 싼 대용치다. 사람 측정을 대신하지는 않는다.

**P3: 프로젝트를 넘는 재사용.** 판정이 붙은 카드가 두 게임 이상에서 쌓인 뒤에 정한다. 그 전에는 `genre-recipes/`를 만들지 않는다.

## 하지 않는 것

- 상주 감독, 다중 에이전트 워크플로, 실행기별 상태 머신.
- 재미의 자동 판정. 비평 모델의 점수로 실험을 닫지 않는다.
- GUI 자동 탐색 에이전트, RL 플레이어.
- 조사 결과의 GDD 자동 반영. supported가 나와도 GDD를 고치는 것은 사용자가 승인하는 별도 `gdd` 작업이다.
- main 머지와 푸시의 자동화.
- 외부 벤치마크 연동.

## 정할 것

1. **카드 형식.** JSON(위 설계, lint가 쉽고 작업 파일과 같은 모양) 대 마크다운(사람이 읽고 승인하기 쉽다). 추천: JSON으로 하고 `approve`가 사람이 읽는 요약을 출력.
2. **실험 브랜치 커밋.** 카드에 `"commit": "branch"`를 허용할지. 허용하지 않으면 묶어서 맡기기(P1)는 작업마다 커밋을 묻는 데서 멈춘다. 추천: 허용(브랜치 커밋만, 머지·푸시는 그대로 사용자).
3. **조사 격리 방식.** 하위 에이전트(추천) 대 리드가 직접 검색. 직접 하면 간단하지만 웹 내용이 리드의 문맥에 그대로 들어온다.
4. **P0를 돌릴 질문.** merc-guild에서 무엇을 물을지. 후보: 마일스톤 1의 열린 질문 "성공 확률을 숫자로 보여 줄지 등급으로 보여 줄지"(2번 칸), 또는 "용병 배정이 계약 결과를 바꾸는가"(1번 칸, 더 싸다. 추천).

## P0 실측 (2026-11-11)

merc-guild에서 한 바퀴 돌렸다: 점검 → 질문 → EXP-001 카드 → lint → 사용자 승인 → 시뮬레이션 작업(`task.mjs start` → 구현 → `verify` → Codex 리뷰 pass). 조사는 하지 않았다(가설 둘이 GDD에서 바로 나왔다). **`gs-research`와 조사 노트는 아직 실제로 써 보지 않았다.**

**실험 결과(EXP-001, 판정은 사용자 확인 전).** 용병이 계약의 `days` 동안 묶인다고 가정하면, 30일 평균 금화는 무작위 928, 탐욕 1068, 저울질 1205(200판). M1 탐욕/무작위 1.151(문턱 1.15), M2 저울질/탐욕 1.128(문턱 1.10). 등록한 측정은 둘 다 통과했다. 다만 시드 묶음 다섯으로 다시 재면 M1은 1.148~1.195로 한 묶음이 문턱 아래다. M2는 1.112~1.152로 모두 넘는다. 즉 "배정이 계산이 아니라 결정이 된다"(M2)는 버티고, "배정이 결과를 크게 바꾼다"(M1)는 문턱에 걸쳐 있다. 이 결과는 시뮬레이션에 넣은 가정(용병 3명, 계약 풀 6종, 하루 2개 제시) 위에서만 참이다.

점검에서 카드 없이 답이 나온 것도 있다: 지금 규칙(용병 1명, 즉시 해결, 실패해도 손실 없음)에서는 "모두 받는다"가 언제나 최선이라 받기·넘기기는 결정이 아니다. 기둥 1·2를 받치는 규칙이 없다는 뜻이다.

**볼 것으로 적었던 네 가지.**

- 카드를 쓰는 시간이 실험보다 긴가: 비슷했다. 질문을 지금 게임에서 물을 수 있게 좁히는 데 가장 오래 걸렸고, 그것은 카드가 없었어도 해야 할 일이었다.
- lint가 잡은 것과 놓친 것: 첫 lint에서 잡은 것은 없다. 카드를 쓴 쪽이 lint를 쓴 쪽이라 뜻이 약하다. 놓친 것은 마찰 1·2·4다(측정과 검사의 관계, 잡음, 가정). 셋 다 형식이 아니라 실험 설계의 문제였다.
- 시뮬레이션이 판단을 바꿨는가: 바꿨다. 만들기 전에는 "탐욕이 곧 최선이라 계산일 것"과 "저울질이 이길 것" 중 어느 쪽인지 몰랐고, 화면 없이 한 시간 안에 답이 나왔다.
