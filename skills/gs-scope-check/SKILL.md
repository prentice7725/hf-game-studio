# 범위 점검

Claude-Code-Game-Studios의 `scope-check` 스킬을 hf-game-studio용으로 줄인 것이다(MIT, NOTICE.md 참고).
읽기 전용이다. 계획 변경은 hyperfusion `project.mjs amend`와 사용자 승인으로 한다.

## 문서 읽기

설계 문서는 통째로 읽지 않는다. 먼저 `grep -n '^#' <문서>`로 제목과 줄 번호를 보고, 필요한 섹션의 줄 범위만 Read의 offset/limit으로 읽는다. 문서가 커질수록 통째 읽기는 토큰을 크게 쓰고, Read 한도(약 2.5만 토큰)를 넘으면 실패한다(원본 템플릿 이슈 #64, #136).
GDD에서는 "범위 밖" 섹션과 작업이 가리키는 규칙 섹션만 본다.

## 점검 항목

1. **작업 크기:** 작업 하나가 한 일꾼의 한 라운드(파일 몇 개, 수용 기준 1~3개)로 끝날 크기인가? 종류가 섞인 작업(예: 초상화 생성 + 화면 연결)은 나눈다.
2. **종류 매핑:** 각 작업의 kind가 실제 내용과 맞는가? (대사 작성이 code로, 이미지가 ui로 잡혀 있지 않은가)
3. **의존 순서:** 데이터 → 규칙 코드 → UI 순서처럼, 앞 작업의 결과물(스키마, 데이터 파일)이 뒤 작업보다 먼저 있는가?
4. **수용 검사:** 각 작업에 컨트롤러가 돌릴 수 있는 검사(스키마, 매니페스트, 스크린샷, 테스트)가 있는가? 없는 작업은 일꾼 말만 믿게 된다.
5. **마일스톤 목표:** 체크포인트 기준이 관찰 가능한 결과(파일 통과, 스크린샷)인가? "재미있다" 같은 기준은 사용자 플레이 확인으로 따로 적는다.
6. **범위 초과:** GDD의 "범위 밖"에 있는 것이 작업에 들어 있는가?
